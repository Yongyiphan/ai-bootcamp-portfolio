Lab 01 — Transforming the CLI Résumé Analyzer into a web app

Wrap Day 4's main.py/analyzer.py/llm.py résumé-scoring pipeline in a Streamlit UI: a file uploader instead of a CLI argument, a text area instead of a JD file path, and the exact same 8-step LLM analysis underneath.

Getting ready

Start from your own Day 4 Résumé Analyzer (llm.py, parse.py, prompts.py, analyzer.py, report.py).

One gap to check before you start: Day 4's original CLI scored keyword match, bullet quality, jargon, and structure — but most Day 4 submissions did not include degree alignment (checking whether the JD's job title fits your degree program). This lab's reference adds it as a fifth scoring component. If analyse_degree_alignment isn't already in your analyzer.py, add it now, before touching app.py — steps below.

How to do it...

  1. Add degree-alignment scoring, if your Day 4 version doesn't have it yet.

    Add this prompt to prompts.py:

    xxxxxxxxxx
    DEGREE_ALIGNMENT_PROMPT = """\
    You are a degree-alignment checker. You are given a JD profile JSON and the
    student's degree program code. You check whether the JD job title is on the
    suggested-titles list for the student's degree.
    

    Degree-Aligned Job Title Lists
    ===============================
    RTIS (Real-Time Interactive Simulation):
      Game Engine Developer, Systems Engineer, Site Reliability Engineer (SRE),
      DevOps Engineer, AI/ML Engineer, Data Analyst / Data Scientist,
      Full Stack Developer, Cybersecurity Engineer, Simulation Engineer,
      Graphics Programmer, Technical Product Manager, Technical Project Manager
    

    IMGD (Interactive Media & Game Development):
      Game Developer, Systems Engineer, Full Stack Developer, Data Engineer,
      Infrastructure Engineer, DevOps Engineer, Cybersecurity Engineer,
      AI/ML Engineer, Technical Designer, Technical Artist,
      Gameplay Programmer, Tools Engineer,
      Technical Product Manager, Technical Project Manager
    

    UXGD (User Experience & Game Design):
      App Developer, UI/UX Designer, Product Designer, Product Manager,
      Product Operations Manager, Project Manager, Marketing & Design Specialist,
      Process Architect, Technical Designer, Technical Artist,
      UX Researcher, UX Engineer
    

    BFA (Digital Art and Animation):
      Technical Artist, UI/UX Designer, Creative Designer, Unreal Engine Artist,
      3D Graphic Artist, Production Assistant, Project Manager, Project Operations
    

    Matching rule:
    - title_on_suggested_list is true if the JD title matches an entry exactly OR
      is a clear variant (e.g. "Junior Systems Engineer" matches "Systems Engineer").
    - If false, set degree_alignment_score to 50-70 with fit_commentary explaining
      the mismatch. Never invent a match.
    

    JSON schema:
    

    {
      "student_degree": "string",
      "jd_title": "string",
      "title_on_suggested_list": true,
      "matched_against": "string",
      "fit_commentary": "string (40 words or fewer)",
      "degree_alignment_score": 100
    }
    

    Output ONLY a valid JSON object matching the schema above. No prose. No
    markdown fences. Never rewrite or generate résumé content.
    """

    Add this function to analyzer.py (import DEGREE_ALIGNMENT_PROMPT alongside your other prompt imports):

    xxxxxxxxxx
    def analyse_degree_alignment(jd_profile: dict, degree_program: str) -> dict:
        """JD profile + degree -> degree alignment dict."""
        user = (
            f"DEGREE PROGRAM: {degree_program}\n\n"
            f"JD PROFILE:\n{json.dumps(jd_profile, indent=2)}"
        )
        return ask_json(DEGREE_ALIGNMENT_PROMPT, user, max_tokens=600)

    Add its 10% weight to compute_overall_score() in analyzer.py (rebalance if your existing weights don't already leave room for it):

    xxxxxxxxxx
    degree = report["degree_alignment"].get("degree_alignment_score", 0)
    total = (
        keyword_score * 0.40
        + bullet_avg  * 0.25
        + structure   * 0.15
        + jargon      * 0.10
        + degree      * 0.10
    )

    Updating report.py's Markdown renderer to print a "Degree Alignment" section is optional for this lab — the Streamlit app below renders degree_alignment with st.json() directly, so the CLI's report.py only needs the change if you still want it in your .md output too.

  2. Confirm your .env points at a model you've actually pulled (or a cloud provider you have a key for):

    xxxxxxxxxx
    MODEL=ollama/gemma3:4b
    OLLAMA_API_BASE=http://localhost:11434

  3. Write app.py, replacing main.py's argparse inputs with Streamlit widgets:

    xxxxxxxxxx
    import streamlit as st
    from dotenv import load_dotenv
    

    from parse import read_resume_pdf
    from analyzer import (
        extract_resume_profile, extract_jd_profile, analyse_keyword_match,
        analyse_bullets, analyse_jargon, analyse_structure,
        analyse_degree_alignment, summarise_overall, compute_overall_score,
    )
    

    load_dotenv()
    VALID_DEGREES = ["RTIS", "IMGD", "UXGD", "BFA"]
    

    st.set_page_config(page_title="Resume Analyzer", layout="wide")
    st.title("📄 AI Resume Analyzer")
    

    resume_file = st.file_uploader("Upload Resume (PDF)", type=["pdf"])
    jd_text = st.text_area("Paste Job Description", height=250)
    degree = st.selectbox("Select Degree", VALID_DEGREES)
    run = st.button("Analyze Resume")
    

    if run:
        if not resume_file or not jd_text:
            st.error("Please upload resume and paste job description.")
            st.stop()
        # ... call read_resume_pdf(resume_file), then each analyse_* function in turn,
        #     exactly as main.py's 8-step pipeline does — see Solutions/ for the full version.

  4. Confirm read_resume_pdf accepts a Streamlit UploadedFile object, not just a path string — pypdf.PdfReader accepts both transparently, so this usually needs no change from your Day 4 version.

  5. Run locally, upload a real résumé PDF and paste a real job posting, and confirm all 8 steps complete with a final score and pass/fail verdict.

  6. Deploy following doc 05 exactly — requirements.txt (litellm, python-dotenv, pypdf, streamlit), push to GitHub, deploy on Streamlit Community Cloud, add your model/API secrets in the Secrets panel.

How it works...

Once step 1's degree-alignment addition is in place (or already there from your own Day 4 version), nothing in analyzer.py, llm.py, prompts.py, or report.py needs to change again for the rest of this lab — everything from here is about the input layer. main.py's CLI took a file path string; app.py's Streamlit version takes an UploadedFile object from st.file_uploader. Because parse.py's read_resume_pdf() was written to accept "a file", not specifically "a path", both callers work against the identical function — the same "layer separation pays off" lesson from doc 03, just discovered instead of built.

If you're running entirely against a local Ollama model, the PDF's own instructions explicitly allow this: "local-AI-only submissions are fine — no hosted cloud AI feature is required, as long as the app itself is live." Streamlit Community Cloud has no access to your laptop's Ollama server, so a purely local-model submission still needs to be deployed and reachable — it just won't be able to call the LLM once deployed unless you also wire in a cloud provider (Gemini, OpenAI, Anthropic) as a fallback. Read the submission requirements for this run of the course carefully on this point before you deploy.

There's more...

This is the same "Day 4 CLI logic becomes a real web app" arc Day 6's Lab mini-project previewed with a much simpler Simple Resume App — same idea (wrap existing logic in st.file_uploader + st.text_area + st.button), scaled up to the full 8-step LLM pipeline instead of local Python logic.

Lab 02 — Decoupling a review-analytics monolith into layers

You're handed a working single-file app, logic.py — a customer-review sentiment analyzer using Gemini and SQLite, all in one file. Your job is to split it into the same four layers doc 03 and doc 04 established: config.py, database/db_manager.py, services/gemini_service.py, and a slimmed-down app.py.

Getting ready

Start from the provided logic.py (Gemini API key, SQLite persistence, a Streamlit sidebar with category filters, all mixed together in one file). Solutions/Lab02_Review_Analytics/ in this folder has the complete decoupled reference if you get stuck.

How to do it...

  1. Extract every os.getenv(...) call and the API-key gatekeeper into config.py:

    xxxxxxxxxx
    import os, sys
    from dotenv import load_dotenv
    load_dotenv()
    

    GEMINI_API_KEY = os.getenv("GEMINI_API_KEY")
    GEMINI_MODEL = os.getenv("GEMINI_MODEL", "gemini-flash-latest")
    DB_NAME = os.getenv("DB_NAME", "review_history.db")
    

    if not GEMINI_API_KEY:
        print("Configuration Error: GEMINI_API_KEY environment variable is missing!")
        sys.exit(1)

  2. Extract every sqlite3.connect(...) function into database/db_manager.py — init_db(), save_summary(), get_summaries_by_category(), get_summary_by_id() — each reading config.DB_NAME instead of a hardcoded filename.

  3. Extract the Gemini call and its rating-parsing logic into services/gemini_service.py, as a single function that returns a clean tuple:

    xxxxxxxxxx
    def analyze_review_sentiment(review_content):
        # ... build the system prompt, call client.models.generate_content(...),
        #     parse out "FINAL_RATING: X", classify into Good/Average/Bad ...
        return clean_summary, rating, category

  4. Slim app.py down to imports, sidebar layout, and three function calls — init_db(), analyze_review_sentiment(), save_summary() — with zero raw SQL and zero genai.Client calls left inside it.

  5. Test against the provided good.txt and bad.txt fixtures — confirm a clearly positive review lands in the "Good" category and a clearly negative one lands in "Bad".

  6. Deploy following doc 05, same as Lab 01.

How it works...

The test of a correct decoupling isn't "does it still run" — a monolith that still runs after a sloppy split just means you got lucky with import order. The real test is: could you hand services/gemini_service.py to a teammate who has never seen app.py, and could they understand what it does without reading anything else? If analyze_review_sentiment() needs to know about st.file_uploader or Streamlit's session state to make sense, the split isn't finished yet — a service module should be usable from a CLI script, a test file, or a completely different UI framework, with zero changes.

There's more...

good.txt/bad.txt aren't just test fixtures — they're a debugging tool. If your refactored version scores good.txt as "Bad" or vice versa, the bug is almost certainly in how you extracted the rating-parsing logic ("FINAL_RATING:" in raw_output, then int("".join(filter(str.isdigit, parts[1])))) — copy that parsing exactly, don't paraphrase it, since a single off-by-one in string splitting silently produces a wrong-but-plausible-looking number.
