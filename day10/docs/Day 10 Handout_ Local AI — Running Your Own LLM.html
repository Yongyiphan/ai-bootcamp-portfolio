1. Why Local AI Matters Now

In earlier sessions you used a cloud inference provider such as Groq to call a hosted LLM from Python. That was a good starting point because it let you focus on prompting, memory, and RAG without worrying about local hardware. Day 10 changes the question: instead of "How do I call an LLM API?", we ask "Can I run the model myself, on my own computer or private server?"

Local AI means the model weights are stored on your own machine or infrastructure and inference happens there. This is not automatically better than cloud AI, but for a growing set of real-world situations, it is the only viable option.

Real-world situations where local inference is not optional

Data privacy and legal compliance

When Samsung engineers used ChatGPT to help debug proprietary chip source code in 2023, the code was uploaded to OpenAI's servers as training data, a breach that led Samsung to ban generative AI tools internally.[*] This pattern repeats across industries. A hospital cannot send patient records to a cloud LLM without violating HIPAA. A law firm cannot paste client contracts into ChatGPT without breaching attorney-client privilege. A bank cannot let trading strategies leave its network. A government agency operating under GDPR cannot use a US-based cloud provider for sensitive citizen data without careful legal structuring. In all these cases, local inference is not a performance choice, it is a compliance requirement.

Air-gapped and offline environments

Many real deployment environments have no reliable internet access: factory floors, offshore platforms, field research stations, military and government systems, and rural healthcare facilities. An AI assistant that requires a cloud API is useless in these settings. A locally-running model on a laptop or edge server works without any network connection after the initial setup — which is exactly what this session's practice project demonstrates.

Cost at scale

Cloud API pricing is designed for moderate usage. At high volume, processing thousands of documents per day, running continuous analysis pipelines, or serving many internal users, the per-token cost accumulates rapidly. A team running 10 million tokens per day at typical GPT-4o-class pricing (roughly $2.50 per million input tokens, $10 per million output tokens — check current provider pricing, as it changes often) would spend somewhere in the region of $2,000–$4,000 per month, and that scales linearly: a larger org-wide deployment at 10× the volume easily lands in five figures monthly. The same workload on a local 7B model running on a single GPU server costs electricity. Once the hardware is paid off, marginal inference cost approaches zero.[11]

Reproducibility and model pinning

Cloud providers silently update their models. Code that worked correctly against GPT-4 in January may produce different outputs in July because the underlying model changed. For scientific research, regulatory submissions, audit trails, or any application where consistent outputs matter, this is a serious problem. A locally-pinned GGUF model file produces identical output every time, the model does not change unless you explicitly pull a new version.

Latency-sensitive applications

Every cloud API call involves a network round-trip to a data centre, queuing behind other users, and the return journey. For interactive applications that need sub-second response times — real-time code completion, live document annotation, on-device voice assistants — this latency is unacceptable. A small local model (1–3B parameters) can respond in under a second on consumer hardware with no network dependency.

☁️ Cloud-first AI

Example: Groq, OpenAI API, Anthropic API, Gemini API. The model runs on provider infrastructure. You send prompts and receive responses through an API.

Good when: you need frontier-quality reasoning, managed infrastructure, rapid prototyping, or the data is not sensitive.

💻 Local / self-hosted AI

Example: Ollama on a laptop, Transformers on a workstation, vLLM on a GPU server, llama.cpp on edge hardware.

Good when: data is sensitive or regulated, internet is unavailable, volume is high, or reproducibility is required.

🧭 Main idea

There is no single "best" local AI tool. Ollama is the fastest path to a working local app. Transformers gives full model control. llama.cpp is strongest for CPU/edge inference. vLLM is for production-scale GPU serving. The right choice depends entirely on the project. This handout covers all of them — the lab focuses on Ollama because it gets you running in minutes.

2. Local vs Cloud AI: The Real Trade-offs

A local model is not simply a free version of a cloud model, it changes the application architecture. With cloud inference, your app sends text to a remote provider. With local inference, the model server may be on localhost, a private lab machine, or a company GPU server. This can reduce data exposure, but it transfers responsibility to you: model selection, updates, memory management, hardware, and monitoring.

Documents stay on your machine. The practice project supports .txt, .md, .py, .csv, .html, .pdf, and .docx. All parsing happens locally using pypdf and python-docx — no upload to any external service.
Chunking splits long documents into overlapping pieces so retrieval can find relevant sections without sending the whole document to the model. Default: 900 characters per chunk, 150 overlap. The Streamlit app (practice 6) lets you tune these live.
A dedicated local embedding model converts text chunks into vectors. We use nomic-embed-text through Ollama. This is a small model (~274 MB) optimised purely for embeddings — much faster than using a chat model for the same task. Vectors are saved to a local JSON file.
Retrieval compares your question's vector to every stored chunk vector using cosine similarity. The top-k most semantically similar chunks are returned. Practice 4 lets you inspect these chunks before attaching the LLM, so you can verify retrieval is working correctly.
Generation: Ollama reads the retrieved chunks and writes a grounded answer. The system prompt instructs the model to use only the provided context and to say "I could not find this" when the answer is not present. This replaces the cloud LLM call from earlier sessions.

3. Model Architecture Refresher: What Runs Locally?

Most modern text-generation LLMs are based on the Transformer architecture.[1] You do not need to derive the mathematics, but understanding what happens inside the model during inference explains two practical questions that come up constantly in local AI work: why does RAM/VRAM matter so much? and why does a longer conversation or bigger document slow things down and use more memory?

The short answers: every model parameter has to live in memory during inference (hence VRAM), and the model needs to keep track of every previous token in the conversation to attend to it (hence the memory cost of long contexts). Click each step below for more detail.

Prompt: The input includes the user instruction, system instruction, retrieved document chunks, and previous conversation turns if used. Everything that goes into context consumes tokens.
Tokenizer: Text is split into tokens — subword pieces, not exactly words or characters. "tokenisation" might become ["token", "isation"]. The context window limit (e.g. 4K, 8K, 128K tokens) is measured in these pieces.
Embeddings: Token IDs become vectors so the model can process relationships numerically. These model-internal embeddings are different from the document embeddings used for retrieval.
Transformer blocks: Attention lets each token look at every other token in the context to decide what is relevant — this is what makes LLMs context-aware. The KV cache stores these attention states to avoid recomputation, and it grows with context length, which is why long contexts need more VRAM.
Logits: The model produces a score for every possible next token. Temperature controls how "peaked" this distribution is: low temperature → the top token is almost always chosen; high temperature → more randomness.
Autoregressive loop: The selected token is appended to the context, then the model repeats the whole process to generate the next one. This continues until an end-of-sequence token or the max-length limit is reached.

Other generative model families

LLMs are not the only generative AI architecture. A GAN uses a generator and discriminator competing with each other. A VAE learns a compressed latent representation. Diffusion models are common in image generation (Stable Diffusion, FLUX). For this session, we focus on Transformer-based LLMs because they are the models you will run through Ollama, llama.cpp, vLLM, or LocalAI.

4. Local AI Tool Landscape: Which Tool for Which Project?

The local AI ecosystem has several layers: model runners, Python frameworks, inference engines, and production serving systems. Comparing them as if they are the same kind of tool causes confusion. The better question is: what problem are you solving?

Ollama

Best for local app integration

Simple CLI and REST API for running and calling local models.[2] Runs on localhost:11434, no authentication needed for local access.[3] Handles model downloading, GPU/CPU selection, and serving automatically. Under the hood it wraps llama.cpp.

Use when: you want a private chatbot, internal document assistant, classroom lab, quick prototype, or a drop-in replacement for a cloud API call — with minimal setup.

Hugging Face Transformers

Best for control and customisation

Provides model classes, tokenizers, generation settings, and loading utilities such as AutoClasses and from_pretrained().[4]

Use when: you need fine-tuning, LoRA/PEFT adapters, custom generation, research experiments, attention/logit inspection, or full control over model internals. Not covered in today's lab — important for when you move beyond using models as-is.

llama.cpp / GGUF

Best for lightweight inference

C++ inference engine with minimal setup. Ollama uses it internally. Also usable directly for maximum performance and fine-grained control.[5]

Use when: you need CPU-first deployment, quantised GGUF models, embedded/edge hardware, or the absolute lowest overhead. If you outgrow Ollama's defaults, go here.

vLLM

Best for production serving

High-throughput serving with PagedAttention, multiple decoding algorithms, streaming, distributed inference, and an OpenAI-compatible API.[6]

Use when: many users call the model simultaneously and you need batching, GPU efficiency, and production deployment. Best supported on Linux + NVIDIA GPU, though AMD ROCm and other backends are increasingly supported. Not needed for single-developer or classroom use.

LocalAI

Best for self-hosted OpenAI-compatible API

Free, open-source alternative to OpenAI-style APIs for local or on-prem inference, supporting LLMs, images, audio, and multiple model families.[7]

Use when: you want a private API server that existing OpenAI-style clients can call with minimal code changes — and you want to keep it fully self-hosted in a company network.

LM Studio / Jan

Best for GUI testing

LM Studio serves local LLMs through a local API server and compatibility endpoints.[8] Jan is an open-source ChatGPT-style desktop app for local or cloud models.[9]

Use when: you want no-code local testing, model comparison, or a personal assistant UI before building an app. Both LM Studio and Jan now run on Windows, Mac, and Linux.

📌 For today's practice: we use Ollama

All six practice scripts use Ollama. Not because it is the most powerful option, but because it gives you the shortest path from zero to a working local LLM: one install command, one pull command, and your Python code barely changes from the Groq calls you already know. Once you understand the pattern, swapping to llama.cpp or vLLM for a real project is straightforward.

5. Hardware Reality: RAM, VRAM, and Quantization

The biggest practical barrier to running local LLMs is memory. Every parameter in a model has to live in RAM (CPU) or VRAM (GPU) during inference. A 7B parameter model stored at FP16 — the precision most open-weight models actually ship in — would need around 14 GB. True full precision (FP32) would need close to 28 GB, more than any consumer GPU. This is where quantization comes in.

What is quantization — and why does it matter?

Quantization compresses each weight into fewer bits, typically 8 or 4. The model becomes much smaller and loads faster, at the cost of a small reduction in numerical precision.[10] For most text generation tasks, the quality difference between FP16 and Q4 is noticeable but often acceptable, especially at 7B+ parameter scales.

This is the reason you can run a "7B model" on a laptop. Without quantization, a 7B model at FP16 would need ~14 GB of VRAM. The same model at Q4 needs ~4.2 GB.

The VRAM formula

A useful rule of thumb from Modal's inference guide:[11]

M = (P × Q/8) × 1.2    where M = VRAM (GB), P = parameters (B), Q = bits per weight, 1.2 = KV cache overhead
≈ 4.2 GB VRAM needed for a 7B model at 4-bit quantization (including KV cache overhead)

💡 Unified memory vs separate VRAM — what this means for your laptop

Most PC laptops have a discrete GPU with its own fixed VRAM pool (typically 4–8 GB), separate from the main system RAM. If a model needs 5 GB and your GPU only has 4 GB, it either fails or falls back to slow CPU inference.

Apple M-series chips and some AMD APU laptops use unified memory, the CPU and GPU share one memory pool. A 16 GB M2 Mac can give ~12–14 GB to a model. A 16 GB AMD APU laptop works similarly.

On Windows or Linux with a discrete NVIDIA/AMD GPU, Ollama will use your VRAM first, and if the model is too large for VRAM, it offloads layers to RAM automatically (slower, but it still runs). The VRAM formula tells you what will fit at full GPU speed.

There are dozens of open-source model families available on Ollama. Three are highlighted here because they cover the main use cases for this session and are well-supported on most laptop hardware. Llama (Meta) is the most widely adopted open-source family — it has the largest fine-tuning ecosystem and is the backbone of many specialised variants. Qwen 3 (Alibaba) is the best all-rounder for small sizes and multilingual tasks. DeepSeek-R1 is specialised for reasoning and math. 7. Ollama API: Using Local Models Programmatically

When Ollama is running, it acts as a local web server at http://localhost:11434. Your Python code talks to it by sending HTTP requests, the same protocol your browser uses to load web pages, but from code instead. All practice files use Python's requests library to do this. No special Ollama SDK is needed.

HTTP requests come in different types called methods. The two you will see here are:

GET — ask the server for information without sending any data (like loading a webpage); and

POST — send data to the server and get a response back (like submitting a form, or sending a prompt and receiving an answer).

The API shape is close to OpenAI's, so if you later want to switch back to a cloud model, the code change is one line.

Key API pattern: the local LLM call

This is the core replacement for the earlier Groq/cloud call. The full implementation is in practice_05_local_doc_qa_cli.py.

Key fragment — chat endpoint
response = requests.post(
    "http://localhost:11434/api/chat",
    json={
        "model": "qwen2.5:1.5b",
        "messages": [
            {"role": "system", "content": system_prompt},
            {"role": "user",   "content": user_prompt}
        ],
        "stream": False,
        "options": {"temperature": 0.2}   # low = factual, grounded
    },
    timeout=120
)
answer = response.json()["message"]["content"]
✅ OpenAI compatibility

Ollama also exposes /v1/chat/completions — the same endpoint format as OpenAI's API. If you have existing code using the openai Python library, you can point it at Ollama by changing only one line: base_url="http://localhost:11434/v1". The rest of the code stays identical.

8. Practice Project: Offline Multi-file Document Q&A

Six scripts that build a local document Q&A chatbot step by step. Run each in order, each one produces a visible result before you move to the next.

Before you run anything: understand the design choices

Why Qwen 2.5 for the practices?

The practice scripts default to qwen2.5:1.5b simply because it is small enough to run on any laptop and was pulled during setup. It is a reasonable choice for a first local model — not the only one, and not necessarily the best for your use case. llama3.2:1b or llama3.2:3b are equally valid alternatives and worth trying. To switch, change the model name in the environment variable before running any script:

for example to swap to a different model without editing code
# macOS / Linux
export LOCAL_LLM_MODEL=llama3.2:3b

# Windows CMD
set LOCAL_LLM_MODEL=llama3.2:3b

The practices use qwen2.5:1.5b as the default. DeepSeek-R1 is an alternative if you want to see the model's reasoning chain before the answer. It's slower, but more transparent about how it reached a conclusion.

No LangChain

Previous sessions used LangChain to connect document loaders, embedders, retrievers, and the LLM. These practices deliberately skip it. When you are learning how a local RAG pipeline works, LangChain abstractions hide exactly the steps you need to understand. Here you write each part yourself — file loading, chunking, embedding, retrieval, prompt building — so you can see where things can go wrong and fix them. Once you understand the pipeline, wrapping it back in LangChain is straightforward.

No ChromaDB — plain JSON instead

Earlier RAG sessions used ChromaDB as the vector store. That remains a valid production choice. For this practice the vector store is a plain JSON file. At classroom scale (a few hundred chunks), brute-force cosine similarity takes under 50ms, fast enough that ChromaDB adds no benefit and only adds a dependency. The JSON file is also human-readable: open it and see every chunk and its embedding. When you scale to thousands of documents, swap in ChromaDB, FAISS, or Qdrant.

nomic-embed-text instead of all-MiniLM-L6-v2

all-MiniLM-L6-v2 through sentence-transformers is a perfectly good embedding model. But for today's practices, nomic-embed-text through Ollama is simpler: same /api/embed call pattern as the chat model, no extra library, fully offline after the initial pull. If you want to switch: pip install sentence-transformers and replace the embed call with SentenceTransformer("all-MiniLM-L6-v2").encode(text).

⚠️ One rule: never use a chat model for embeddings

Chat models like Qwen can technically return a vector — but they are 5–10× larger, slower, and not trained for semantic similarity. Always use a dedicated embedding model for any RAG pipeline. nomic-embed-text at 274 MB does this job better than a 1.5B chat model.

practice_02_load_many_files.py
Parse .txt, .md, .py, .csv, .html, .pdf, .docx from a docs/ folder into plain Python strings.
▼

Before any chunking or embedding can happen, documents need to be in plain text. Every format needs its own parser. This script normalises everything into a plain Python string so the rest of the pipeline never needs to know what format a file originally was.

What reads what — and why these libraries and not LangChain loaders

LangChain has document loaders for all these formats. We use raw libraries here so you can see exactly what text comes out — LangChain loaders add metadata wrapping that is helpful in production but obscures what is happening during learning.

  • .txt / .md / .py / .csv / .html — plain Path.read_text(). Already UTF-8 text, no library needed. errors="ignore" skips invalid bytes common in Windows-exported CSV files.
  • .pdf — pypdf. Pure Python, no C compiler, works offline. Extracts the text layer page by page. Only works on digital PDFs — scanned PDFs are images of text, pypdf returns empty strings for those.
  • .docx — python-docx. Reads Word document XML. Extracts paragraph text; tables and images are ignored today.
one dispatcher handles all formats
if suffix in {".txt", ".md", ".py", ".csv", ".html"}:
    text = path.read_text(encoding="utf-8", errors="ignore")
elif suffix == ".pdf":
    text = read_pdf_file(path)    # pypdf: page by page
elif suffix == ".docx":
    text = read_docx_file(path)   # python-docx: paragraph text
put test files in docs/ then run
python practice_02_load_many_files.py
practice_03_chunk_embed_store.py
Split text into overlapping chunks → embed each chunk locally → save to a JSON vector store.
▼

You cannot paste a full document into a local LLM — it would exceed the context window, and even if it fit, the model would struggle to focus on anything specific. Documents are split into small pieces that can be individually embedded and retrieved. Run this once; practices 4 and 5 reuse the output without re-embedding.

Chunking with overlap — why the step is smaller than the chunk size

A hard split at fixed intervals risks cutting a sentence in two, putting half the answer in each chunk so neither chunk alone scores highly on retrieval. Overlap (default: 150 characters) means consecutive chunks share text. Any answer near a boundary is covered by at least one complete chunk.

sliding window — step is 750, chunk is 900
while start < len(clean):
    chunk = clean[start : start + chunk_size]   # 900 chars
    chunks.append(chunk)
    start += chunk_size - overlap               # advance 750, overlap = 150

Embedding via Ollama — slow once, reused forever

Each chunk is sent to nomic-embed-text via /api/embed and returns 768 floats. About 0.3s per chunk — slow, but it only happens once. Everything is saved to local_vector_store.json and reused in practices 4 and 5.

what each record looks like in the JSON file
{
    "id":          "report.pdf::chunk_0003",
    "filename":    "report.pdf",
    "chunk_index": 3,
    "text":        "...the chunk text...",
    "embedding":   [0.052, -0.120, 0.334, ...]   # 768 floats
}
run — takes 30–90 seconds depending on document size

How semantic retrieval works

Your question is embedded into a 768-dimensional vector using the same nomic-embed-text that embedded the chunks. Then cosine similarity is computed between the question vector and every stored chunk vector. The top-k highest-scoring chunks are returned. No keyword matching — semantically similar text scores high even if it uses different words.

cosine similarity — pure Python, no NumPy needed
def cosine_similarity(a, b):
    dot    = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    return dot / (norm_a * norm_b) if norm_a and norm_b else 0.0

Cosine measures angle between vectors, not distance. Embedding vectors encode meaning in direction, not length — a short and a long chunk on the same topic point in the same direction. Euclidean distance would penalise length differences that have nothing to do with meaning.

Reading the scores

  • 0.80+ — strong match, this chunk almost certainly contains the answer
  • 0.60–0.80 — relevant, probably useful context
  • below 0.50 — weak match; the answer may not be in your documents

Why the system prompt is critical for small local models

Without an explicit grounding instruction, sub-3B models blend their training knowledge with the retrieved context and may confidently give answers that are not in your documents. This instruction prevents that:

grounded prompt pattern
system = (
    "You are a careful local document assistant. "
    "Answer using ONLY the provided sources. "
    "If the answer is not in the sources, say: "
    "'I could not find this in the provided documents.' "
    "Cite sources using [Source 1], [Source 2], etc."
)

Temperature 0.2 — low enough for factual, consistent answers; not so low the model becomes rigid. For document Q&A, focused beats creative.

The key Streamlit concept: session state

Streamlit re-runs the entire script on every user interaction — every button click, every keystroke. Without session state, the vector index would be rebuilt and all documents re-embedded on every action. st.session_state keeps objects alive across reruns:

9. Benchmarking: What Should You Measure?

Benchmarking should not be only "which answer sounds better?" A useful local AI comparison includes speed, memory pressure, answer grounding, and refusal behaviour. For this bootcamp, keep the benchmark simple: same question, same retrieved chunks, compare response time and a short human quality score.

MetricHow to measureWhy it matters
LatencySeconds from request to complete response (time.perf_counter())Shows whether the model is usable interactively
Answer groundingDoes it cite and use the provided chunks?Critical for document Q&A reliability
Refusal behaviourAsk a question not in the documentChecks whether the model invents unsupported answers
CompletenessDoes it include the important details?Small models may omit key points
Resource usageTask Manager / Activity Monitor / nvidia-smiShows hardware feasibility for production
✅ Good benchmark question set

Use one factual question clearly answered in the document, one summary question, one comparison question, and one question that is not answered in the documents. This tests speed, grounding, and refusal behaviour, not just surface fluency. Compare at least two model sizes if your hardware allows (e.g. qwen2.5:1.5b vs qwen2.5:3b).

10. Security and Privacy: Data Path Matters

"Installed locally" does not mean all AI processing is local. Some desktop AI tools use a local UI but send prompts to a cloud model. For sensitive work, the key question is not "Did I install something?" but "Where does the prompt go during inference?"

  • Fully local path: document → local embedding model → local vector store → local LLM endpoint → local answer. This is what practices 01–06 build.
  • Cloud-assisted path: document or prompt is sent to a hosted model or external API, even if the UI is local.
  • Hybrid path: retrieval is local, but generation is cloud-based, or vice versa.

For coding assistants and AI IDEs, check privacy settings, telemetry toggles, and whether code snippets are sent to external providers. This is not the same as saying any specific tool is unsafe, the professional framing is that cloud-connected tools may create a data-governance risk depending on your project and jurisdiction (GDPR, HIPAA, internal policy).

✅ What "fully local" means in this project

  • Documents never leave your machine
  • Embeddings computed locally via Ollama
  • Vector store saved to local JSON file
  • LLM inference on localhost:11434
  • Works with no internet after setup

⚠️ Things that would break local privacy

  • Switching model to an OpenAI API key
  • Using a cloud embedding service
  • Storing vectors in a cloud vector DB
  • Sending documents to a hosted OCR service
  • Logging prompts/responses to a remote server
